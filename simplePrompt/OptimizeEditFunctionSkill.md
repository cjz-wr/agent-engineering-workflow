### 必须遵守的文件处理顺序与规则

1. **阅读理解 readme.md**  
   优先阅读项目说明文件，确保后续所有修改都符合项目定位和整体设计。  
   - **按需使用文件读取工具读取内容，避免一次性加载整个项目，以节省 token。**

2. **更新项目提示词文件 promot.md**  
   根据新功能，调整或补充 AI 提示词/指令说明。  
   - **只读取和修改必要部分。**

3. **在 plan.md 中列出修改计划清单（仅列出，不修改代码）**  
   - 使用 Markdown 任务列表格式，所有任务初始状态为未勾选 `- [ ]`。  
   - 覆盖 readme、promot、代码、tree 等所有待修改部分。  
   - **此时仅通过文件列表和关键片段理解项目结构，不读取完整文件内容，除非必要。**

4. **Git 安全准备（自主执行）**  
   在进行任何代码修改前，主动使用 Git 命令保障工作安全：  
   - 执行 `git status` 检查工作区状态。若存在未提交的变更，自动暂存并提交（或提示用户处理，由上下文决定），避免丢失工作。  
   - 执行 `git branch` 查看当前分支，**主动创建新功能分支**进行修改，分支名格式建议 `feature/功能简称`。  
   - 切至新分支，绝不在主分支（`main`、`master`、`develop`）上直接修改，除非用户明确指令且风险已确认。

5. **按照计划逐步修改代码**  
   - 严格依据 plan.md 清单逐项实施改动。  
   - **每完成一项代码修改，立即执行编译或语法检查**（使用相应命令）。若失败，分析错误摘要并修复后重新检查，通过后方可继续。  
   - **优先使用局部编辑工具**，减少全文件输出。

6. **变更审查与 Git 提交（自主执行）**  
   - 每完成一个逻辑单元并通过检查后，自主执行 `git diff` 审查变更，确认无意外修改且无敏感信息（密钥、密码等）硬编码。  
   - 若有敏感信息，立即停止并告知用户。  
   - 自主使用 `git add` 添加文件，并以规范信息提交（格式如 `[feat] 描述` 或 `[fix] 描述`）。  
   - 不执行强制推送等破坏性操作，除非用户明确要求且已确认备份。

7. **按需更新文件树描述 tree.md**  
   若文件增删或职责变化，使用 Git 状态或文件列表确认变更，更新 tree.md，并将其纳入提交。

8. **更新项目说明文件 readme.md**  
   所有修改验证通过后，依据变更内容同步更新 `readme.md`，确保项目说明与最新状态一致。  
   - **使用 Git 变更摘要聚焦修改点，避免全文重写。**

9. **回到 plan.md 勾选已完成的任务**  
   确认所有改动无误（含 readme.md、tree.md），将 `plan.md` 中对应 `- [ ]` 改为 `- [x]`，未完成项可附加备注。

### 高效与安全操作原则

- **按需加载**：通过文件浏览、关键词搜索定位修改位置，仅读取相关片段。
- **增量修改**：支持替换/插入时输出增量内容，避免完整文件输出。
- **命令摘要**：编译或检查命令只获取关键错误信息，避免冗长日志。
- **Git 自主性**：在非破坏性操作（分支创建、提交、diff 检查等）上可直接执行，无需用户确认；破坏性操作（rebase、reset、push --force）必须得到用户明确许可。
- **渐进理解**：先结构信息再深入细节。
- **上下文精简**：及时清理不再需要的中间信息。

请严格遵循以上顺序与原则，确保每一步有记录、每次代码变动经编译验证并纳入 Git 控制，完成修改后务必更新 readme.md 文档。
